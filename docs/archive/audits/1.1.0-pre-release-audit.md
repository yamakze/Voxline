### 一、静态性能问题

#### 1. 播放器 30 FPS 高频时钟下的全量对象重算与 View 根层级重绘

• 定位：
• MediaPlaybackController.swift:140-146, 245-267
• MediaDetailProofreadingView.swift:44
• 问题分析：

1. MediaPlaybackController 挂载了 30Hz（每 33ms 一次）的 addPeriodicTimeObserver。每帧均调用 subtitleTimeline.interval 并执行
   .cueIndices.map {
   subtitles[$0] }，高频分配包含 UUID、String、Translation 等完整值类型的 [SubtitleCue] 数组。
2. 随后执行 activeSubtitles != active 对数组逐字段 O(K) 比较；同时在主线程高频修改 @Observable 发布的 currentTimeSeconds。
3. MediaDetailProofreadingView.swift:44 在根 body 中读取了 let activeCue = playbackController.
   activeSubtitle，但子视图根本不消费该变量（详见第五节）。这导致在播放期间，整个详情视图根层级被每秒强制重绘 30 次。
   • 收敛方案：
1. updatePlaybackTime 中优先比对命中的时间区间索引或 cueIndices（[Int]），未变动时直接返回，避免每帧分配 [SubtitleCue]。
2. 移除 MediaDetailProofreadingView.body 顶层对 playbackController.activeSubtitle 的无效依赖，将高频变化的播放状态严格下沉至独立的叶子视图（HUD
   和时间滑块）。

#### 2. SubtitleImporter.plainText 在循环中重复动态编译正则与多轮全量字符串复制

• 定位：
• SubtitleImporter.swift:114-127
• SubtitleImportReader.swift:101
• 问题分析：
plainText 每解析一条字幕即被调用一次。内部通过 replacingOccurrences(..., options: [.regularExpression]) 处理 HTML
标签与时间标签，每次调用均动态重新编译正则表达式；随后连续执行 6 轮 replacingOccurrences
实体替换，在长视频数千条字幕导入场景下会造成不必要的正则编译与多轮堆内存分配。
• 收敛方案：
使用 static let 预编译 Swift Regex，实体替换收敛为单遍遍历匹配或直接使用静态字典映射替换。

#### 3. SubtitleImportSheet 列表渲染与搜索过滤未做缓存与防抖

• 定位：
• SubtitleImportSheet.swift:352-353, 480-485
• 问题分析：

1. let counts = cueAssignmentCounts 为计算属性，在每次 translationAssignmentsPreview 渲染时全量遍历全部 assignments
   构造词频字典。
2. TargetCuePickerSheet 中的 filteredCues 随着搜索框每键入一个字符，在主线程对全量 allCues 做同步的
   localizedCaseInsensitiveContains
   线性扫描，缺乏防抖与预索引。
   • 收敛方案：
   将 cueAssignmentCounts 缓存至 SubtitleImportSession 中，仅在 assignments 发生增删改时更新；搜索过滤增加简易防抖或提前生成小写文本缓存。

#### 4. loadIOSAppIcon 在 SwiftUI View 评估中同步执行 Bundle 与磁盘 I/O

• 定位：
• AppUpdatesSettingsView.swift:24, 39-64
• 问题分析：
AppIconView 的 body 每次求值时（如视图出现、状态刷新、系统主题变化），均同步读取 Bundle.main.infoDictionary 解析嵌套
plist、尝试通过 UIImage(named:) 与
UIImage(contentsOfFile:) 探测文件系统。
• 收敛方案：
将其收敛为 private static let cachedIOSAppIcon: UIImage? 静态常量单例，启动仅求值一次。

#### 5. MacUpdater.deferredInstallation 未取消旧 Task 存在泄漏风险

• 定位：
• MacUpdater.swift:40-52
• 问题分析：
若 Sparkle 代理回调多次触发延后安装请求，直接对 deferredInstallation 重新赋值而未先调用旧任务的 .cancel()，导致之前的后台
Task 依然在自旋等待并持有旧的
installHandler 逃逸闭包。
• 收敛方案：
赋值前调用 deferredInstallation?.cancel() 显式取消旧任务。

### 二、架构与抽象收敛

### 三、由代码维护且对用户无意义的产品概念与交互设计

#### 1. 明确主动触发替换后强加冗余的“二级确认覆盖弹窗”

• 定位：
• SubtitleImportSheet.swift:115-118, 143-160
• 问题分析：
在校对页菜单中，入口按钮在已有字幕时已明确标为“替换原文字幕…”（MediaDetailProofreadingView.swift:105）。用户主动点击进入
Sheet、选择文件并在预览界面检查对比后点击右上角“完成”。此时再次弹出 confirmationDialog
询问“覆盖已有原文字幕？”，属于非破坏性常规编辑流程中的多余阻断（用户随时可以取消或按 ⌘Z 撤销）。
• 收敛方案：
直接点击“完成”即保存替换，移除多余的二次确认弹窗。

#### 2. 将底层匹配实现细节以警戒色暴露给用户（“多对一合并”橙色胶囊）

• 定位：
• SubtitleImportSheet.swift:379-390
• 问题分析：
“多对一合并”是多个翻译片段对齐到单句原文 Cue 时的内部映射状态。使用橙色（Apple HIG 中代表 Warning/Attention
的警戒色）显式打上“多对一合并”标签，容易给用户造成“字幕导入发生冲突/出错”的焦虑与困惑。
• 收敛方案：
降级为次要的灰色轻量元标签（如 .secondary），或仅在需要手动排查时辅助展示，去除错误警示感。

#### 3. “改用语音识别”不可逆全量擦除缺乏数据保全

• 定位：
• MediaDetailProofreadingView.swift:249-264
• IOSMediaDetailView.swift:195-207
• 问题分析：
“改用语音识别”将 cues 与 checkpoint 全量清空。若用户在导入字幕后已进行大量校对，一旦误触将永久丢失所有编辑成果且无法撤销。
• 收敛方案：
支持通过 UndoManager 撤销该操作，或在清空前保留上一版本的编辑快照。

#### 1. 重复三处的冗长稳定排序闭包

#### 2. ReleaseVersion 解析过度防御且断言过于生硬

• 定位：
• ReleaseVersion.swift:11-20
• 代码片段：
guard components.count == 3,
components.allSatisfy({ !$0.isEmpty && $0.allSatisfy(\.isASCII) && $0.allSatisfy(\.isNumber) }),
components.allSatisfy({ Int($0) != nil }) else { throw ReleaseUpdateError.invalidVersion }

• 问题分析：
既检查了 ASCII 纯数字，又重复调用 Int($0) != nil；且硬编码 count == 3 会导致两段式版本号（如 1.0）直接被视作非法版本。
• 收敛方案：
精简为标准的版本号分割映射 components.compactMap(Int.init)，放宽分段长度限制。

#### 3. 核心领域模型中的强制解包隐患

• 定位：
• SubtitleTimeline.swift:27-29：
let change = changes[time]!
active.subtract(change.ending)
active.formUnion(change.starting)

      • SubtitleEditing.swift:72：endMilliseconds: originals.map(\.endMilliseconds).max()!

• 问题分析：

1. 核心模型库使用 ! 强行解包降低代码健壮性。
2. SubtitleTimeline 中，若输入区间存在零时长（start == end），先执行 subtract(change.ending) 再执行 formUnion(
   change.starting)

   • 收敛方案：
   使用安全解包守卫；修正时间扫描逻辑，确保起始与结束操作顺序正确。
